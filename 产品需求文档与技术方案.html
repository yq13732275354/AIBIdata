第一部分：产品需求文档（PRD）

1. 背景与目标

1.1 问题与场景

当前企业数据分析存在以下痛点：

  • 取数门槛高：业务人员需依赖数据团队写 SQL 取数，排期长、沟通成本高，无法做到"即问即答"。
  • 报告编制繁琐：周报/月报/经营分析报告需人工找数、手工分析、截图整理，耗时且易出错。
  • 洞察提取困难：仪表板数据丰富，但异常识别、波动归因、趋势解读依赖人工经验，难以规模化。

1.2 产品定位

面向销售与经营分析场景的 AI 智能分析 Agent，让业务人员通过自然语言完成数据查询、解读和报告生成，实现"人人都是数据分析师"。

1.3 参考产品

参考阿里云 Quick BI 智能小Q（羚羊）的三大核心 Agent 能力进行设计：

Quick BI 智能小Q本项目对应模块核心能力
小Q问数 Agent智能问数自然语言问数、多轮对话、意图澄清、波动归因
小Q解读 Agent智能解读指标异常检测、根因分析、数据洞察生成
小Q报告 Agent智能报告一句话生成分析报告、结构化洞察、可编辑

1.4 目标

  • 用户可用自然语言提问，无需编写 SQL 即可获取销售数据结果。
  • 用户可用一句话生成包含指标摘要、趋势分析、异常洞察的结构化报告。
  • 输出结果包含可视化图表、数据表格和文字洞察，支持多轮追问深入分析。

2. 范围定义

2.1 数据基础

用户将提供一份销售数据作为数据基础。当前文档基于典型销售数据结构进行设计，实际字段以用户提供的数据为准。
假设的销售数据结构（待用户确认后调整）：
  • orders 订单表：order_id, order_date, customer_id, product_id, region, channel, quantity, amount, discount
  • products 产品表：product_id, product_name, category, subcategory, cost_price, selling_price
  • customers 客户表：customer_id, customer_name, region, segment
核心指标：销售额(sales_amount)、销量(quantity)、利润(profit)、客户数(customer_count)；核心维度：时间、地区、产品类别、渠道。

4. 功能需求 — 智能问数

FR-A1：数据集选择与加载

目的：用户选择要查询的销售数据集，系统加载其 Schema。

  • 触发：用户进入问数界面，或上传新的销售数据文件。
  • 处理规则：
    • 系统读取数据文件（CSV/Excel），自动推断字段名与类型。
    • 数据管理员可为每个字段补充中文描述（用于 NL2SQL 的 Schema 注入）。
    • 系统将数据加载到分析引擎（DuckDB），生成可查询的表。
  • 结果：数据集就绪，用户可开始提问；界面显示数据集名称与字段概览。
  • 异常：文件格式不支持 → 提示支持的格式；字段解析失败 → 标记异常字段并提示人工确认。

FR-A2：自然语言提问

目的：用户以自然语言输入数据查询需求。

  • 触发：用户在对话框输入问题并发送。
  • 处理规则：
    • 支持文本输入；提供常用问题快捷入口（如"本月销售额"、"各地区销量对比"）。
    • 系统首先进行意图分类（ask_data / interpret / generate_report / chat）。
    • 若为 chat 意图，直接由对话模型回复，不进入数据分析链路。
  • 结果：问题被路由到对应的处理链路。

FR-A3：意图识别与槽位抽取

目的：从自然语言中解析查询所需的结构化信息。

  • 触发：意图判定为 ask_data。
  • 处理规则：
    • LLM 从用户问题中抽取以下槽位：
      槽位说明示例
      metrics 指标要查询的度量销售额、销量、利润
      dimensions 维度分组/筛选维度地区、产品类别、渠道
      time_range 时间范围查询的时间区间上个月、2024年Q3
      filters 过滤条件限定条件华东区、电子产品
      aggregation 聚合方式sum/avg/count/topN总和、平均、前10
    • 时间表达需规范化（"上个月"→ 具体日期区间）。
    • 输出结构化 JSON，供后续 NL2SQL 使用。
  • 结果：得到结构化的查询意图 JSON。

FR-A4：缺失槽位澄清

目的：当关键信息缺失时，主动向用户追问，避免生成错误 SQL。

  • 触发：槽位抽取后，关键槽位（指标或时间范围）为空。
  • 处理规则：
    • 仅追问最小必要槽位，不一次性问所有缺失项。
    • 澄清话术应简洁明确，如："请问您想查询哪个时间范围的销售额？"
    • 用户回复后，将新信息合并到当前会话槽位，继续后续流程。
    • 若用户连续两轮无法提供有效信息，给出查询示例引导。
  • 结果：槽位补全后进入 NL2SQL；或用户放弃查询。

FR-A5：NL2SQL 生成与校验

目的：将结构化意图转换为可安全执行的 SQL。

  • 触发：槽位完整。
  • 处理规则：
    • LLM 接收：数据集 Schema（表名+字段+描述）+ 槽位 JSON + 少量 Few-shot 示例。
    • LLM 输出结构化 JSON：{"sql": "...", "chart_type": "bar", "explanation": "..."}。
    • 安全校验（本地 AST 级规则，不依赖 LLM 自觉）：
      1. 仅允许 SELECT 语句，禁止 INSERT/UPDATE/DELETE/DROP。
      2. FROM 表名必须在 Schema 白名单内。
      3. 引用的列名必须在 Schema 白名单内。
      4. 禁止子查询中出现写操作（递归校验）。
    • 校验失败 → 自动重试（最多 2 次），仍失败则返回错误并展示问题。
  • 结果：得到可执行的 SQL 或明确的错误提示。

FR-A6：SQL 执行与结果格式化

目的：执行查询并将结果转为前端可展示的结构。

  • 触发：SQL 校验通过。
  • 处理规则：
    • 在分析引擎（DuckDB）中执行 SQL，设置超时（如 30s）。
    • 结果转为 JSON：{"columns": [...], "rows": [[...], ...]}。
    • 若结果为空 → 返回空结果提示，并建议调整条件。
    • 若结果行数超过阈值（如 1000 行）→ 截断并提示，避免前端渲染压力。
  • 结果：结构化的查询结果数据。

FR-A7：多轮对话上下文管理

目的：支持用户基于上一轮结果继续追问，无需重复说明全部条件。

  • 触发：同一会话内的后续提问。
  • 处理规则：
    • 会话维护一个槽位状态（指标、维度、时间、过滤条件）。
    • 每轮提问先抽取新槽位，再与上一轮状态合并：
      • 用户明确指定的维度/指标 → 覆盖旧值。
      • 用户未提及但上一轮已有的 → 继承。
      • 用户说"换个维度"/"加上XX" → 追加或替换。
    • 时间范围继承：若新问题未提时间，沿用上次时间范围。
    • 支持"上钻/下钻"语义：如"再按产品类别细分" → 在上一轮维度基础上增加维度。
  • 结果：用户可通过连续提问逐步深入分析。

5. 功能需求 — 智能解读与报告

FR-B1：一句话生成报告

目的：用户输入主题或时间范围，系统自动生成结构化分析报告。

  • 触发：意图判定为 generate_report，如"生成一份10月销售分析报告"。
  • 处理规则：
    • 系统根据报告主题，自动规划报告章节（摘要 → 关键指标 → 趋势分析 → 维度拆解 → 异常洞察 → 结论建议）。
    • 每个章节调用问数链路获取对应数据，生成图表与洞察。
    • 报告以结构化文档形式呈现，各章节可独立展开/收起。
  • 结果：生成一份包含指标卡片、图表、文字洞察的完整报告。

FR-B2：自动洞察生成

目的：对查询结果自动生成有价值的数据洞察，而非仅返回原始数据。

  • 触发：每次问数或报告章节生成后。
  • 处理规则：
    • 趋势洞察：识别环比/同比变化方向与幅度。
    • 对比洞察：Top-N 维度成员的排名与占比。
    • 异常洞察：基于统计方法（如 z-score > 2）识别异常值并标注。
    • 洞察由 LLM 基于数据结果生成自然语言描述，要求结论有数据支撑。
  • 结果：每条查询结果附带 1-3 条文字洞察。

FR-B3：报告追问与细化

目的：用户可对报告中的某个章节或指标进行追问深入。

  • 触发：用户针对报告某部分提问，如"华东区为什么下降？"。
  • 处理规则：
    • 系统识别用户追问的章节上下文，继承该章节的指标与时间范围。
    • 进入问数链路执行更细粒度的查询，返回新的图表与洞察。
    • 追问结果可追加到报告中，或作为独立分析展示。
  • 结果：报告可交互式深入，而非一次性静态产物。

FR-B4：报告导出

目的：将生成的报告导出为可分享的文件。

  • 触发：用户点击报告的"导出"按钮。
  • 处理规则：
    • P1支持导出为 PDF / Word（.docx）。
    • P0支持导出为 HTML（自包含，含图表）。
    • 导出内容包含报告标题、生成时间、所有章节的图表与洞察。
  • 结果：用户获得可下载的报告文件。

6. 功能需求 — 可视化输出

FR-C1：自动图表类型选择

目的：根据查询结果的数据特征，自动选择最合适的图表类型。

  • 触发：查询结果返回后。
  • 处理规则（基于数据结构的规则引擎）：
    数据特征推荐图表示例
    时间维度 + 1 个指标折线图月度销售额趋势
    分类维度 + 1 个指标（≤10类）柱状图各地区销售额
    分类维度 + 1 个指标（占比场景）饼图各渠道销售额占比
    2 个维度 + 1 个指标堆叠柱状图 / 分组柱状图各地区各品类销售额
    仅 1 行聚合结果指标卡片本月总销售额
    维度数 ≥ 3 或结果行数 > 20表格详细明细数据
  • 结果：系统返回推荐图表类型及配置，前端渲染。

FR-C2：图表渲染

目的：将查询结果可视化为交互式图表。

  • 支持图表类型：柱状图、折线图、饼图、散点图、堆叠柱状图、指标卡片。
  • 交互能力：鼠标悬停显示数值、图例切换、坐标轴缩放。
  • 样式：统一配色方案，支持深色/浅色主题。

FR-C3：表格展示

目的：以表格形式展示明细或多维度数据。

  • 功能：列排序、分页、数值格式化（千分位、百分比、小数位）。
  • 触发：数据不适合图表展示，或用户明确要求看表格。

FR-C4：单图表/表格导出

目的：用户可导出单个分析产物。

  • 图表导出为 PNG 图片。
  • 表格导出为 CSV 文件。

7. 共享规则与异常处理

7.1 SQL 安全规则

  • 所有 SQL 必须通过 AST 级白名单校验，仅允许只读 SELECT。
  • 禁止访问系统表与未授权表。
  • 执行超时强制中断，防止恶意长查询。

7.2 响应结构规范

所有 Agent 返回统一的结构化响应，前端按类型渲染：

{
  "intent": "ask_data",
  "answer": "10月华东区销售额为 1,250 万元，环比增长 8.3%。",
  "artifacts": [
    {"type": "chart", "chart_type": "bar", "data": {...}, "config": {...}},
    {"type": "table", "columns": [...], "rows": [...]}
  ],
  "insights": ["华东区销售额创近6个月新高", "主要增长来自电子产品品类"],
  "sql": "SELECT ...",
  "slot_state": {...}
}

7.3 异常处理矩阵

异常场景系统行为用户提示
LLM 调用失败/超时重试 1 次，仍失败则降级"AI 服务暂时不可用，请稍后重试"
SQL 校验失败自动重试 2 次，仍失败则返回错误"无法理解您的问题，请换一种说法"
SQL 执行超时中断查询"查询耗时过长，请缩小范围"
查询结果为空返回空状态"未找到匹配数据，请尝试调整筛选条件"
数据文件读取失败中止加载"文件格式不支持或已损坏，请检查后重新上传"
槽位连续缺失提供示例引导"您可以这样问：上个月各地区的销售额是多少？"

7.4 数据隐私

  • LLM 调用时仅传递 Schema（字段名+描述）和聚合结果，不传递原始明细行（除非用户明确要求明细）。
  • API 密钥仅从环境变量读取，不硬编码、不打印日志。
  • 日志中对 SQL 结果做脱敏（仅记录行数与列名）。

8. 待确认问题（Open Questions）

  1. 销售数据结构：用户将提供的销售数据具体包含哪些表和字段？当前基于典型结构假设，需确认后调整 Schema 与示例。
  2. LLM 选型：使用哪个大模型？（DeepSeek / Qwen / OpenAI / 其他）需确认 API 可访问性与成本。
  3. 部署方式：本地运行还是服务器部署？是否需要 Docker 化？
  4. 前端形态：MVP 阶段使用 Streamlit 快速搭建，还是需要独立的 React 前端？
  5. 并发与用户量：MVP 预计多少用户同时使用？影响是否需要引入会话管理与限流。

第二部分：技术方案

1. 总体架构

系统采用分层架构，自上而下分为交互层、API 网关层、Agent 编排层、能力服务层、数据存储层。

┌──────────────────────────────────────────────────────────────┐ │ 交互层 (Frontend) │ │ 对话界面 │ 报告查看器 │ 图表渲染 (ECharts) │ └───────────────────────────┬──────────────────────────────────┘ │ HTTP / SSE (流式响应) ┌───────────────────────────▼──────────────────────────────────┐ │ API 网关层 (FastAPI) │ │ 路由分发 │ 会话管理 │ 鉴权 │ 流式响应 │ 异常处理 │ └───────────────────────────┬──────────────────────────────────┘ │ ┌───────────────────────────▼──────────────────────────────────┐ │ Agent 编排层 (LangGraph) │ │ ┌──────────┐ ┌────────────┐ ┌──────────┐ ┌───────────┐ │ │ │ 意图路由 │→│ 问数 Agent │ │ 解读Agent │ │ 报告Agent │ │ │ │ Router │ │ AskAgent │ │InsightAg │ │ReportAgent│ │ │ └──────────┘ └─────┬──────┘ └─────┬────┘ └─────┬─────┘ │ └──────────────────────┼───────────────┼─────────────┼────────┘ │ │ │ ┌──────────────────────▼───────────────▼─────────────▼────────┐ │ 能力服务层 (Services) │ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌───────────────┐ │ │ │ NL2SQL │ │ 洞察引擎 │ │ 可视化 │ │ 报告组装 │ │ │ │ Engine │ │ Insight │ │ Viz │ │ Report │ │ │ └──────────┘ └──────────┘ └──────────┘ └───────────────┘ │ └──────────────────────────────────────────────────────────────┘ │ ┌───────────────────────────▼──────────────────────────────────┐ │ 数据存储层 (Storage) │ │ DuckDB (分析查询) │ SQLite (元数据/会话) │ 文件系统 (产物) │ └──────────────────────────────────────────────────────────────┘

架构设计原则

  • Agent 显式状态：使用 LangGraph 管理会话状态（槽位、历史消息），而非隐式上下文拼接。
  • 能力与编排分离：NL2SQL、洞察、可视化等作为独立 Service，Agent 仅负责编排调用，便于复用与测试。
  • 安全前置：SQL 执行前必经 AST 校验层，不依赖 LLM 自觉。
  • 流式响应：通过 SSE 向前端流式输出文字与产物，提升交互体验。

3. 模块级设计

3.1 意图路由（Intent Router）

作为入口的第一个节点，决定请求走向哪个 Agent。

  • 输入：用户问题 + 会话历史。
  • 方法：LLM 输出结构化意图分类（ask_data / interpret / generate_report / chat）。
  • 路由：
    • ask_data → 问数 Agent
    • interpret → 解读 Agent
    • generate_report → 报告 Agent
    • chat → 直接对话回复

3.2 问数 Agent（AskAgent）

核心链路：意图 → 槽位 → 澄清判断 → NL2SQL → 校验 → 执行 → 可视化。

用户问题 │ ▼ [槽位抽取] ──► 槽位状态合并（继承上一轮） │ ▼ 关键槽位缺失？ ──是──► [澄清回复] │否 ▼ [NL2SQL 生成] (Schema + 槽位 + Few-shot) │ ▼ [SQL AST 校验] ──失败──► 重试(≤2) ──► 错误回复 │通过 ▼ [DuckDB 执行] ──超时/异常──► 错误回复 │成功 ▼ [结果格式化] ──► [自动洞察] ──► [图表选择] ──► 结构化响应

3.3 NL2SQL 引擎

  • Prompt 构造：
    • System：角色设定 + SQL 生成规则（仅 SELECT、必须用白名单字段、时间过滤写法）。
    • Schema：表结构（表名、字段名、类型、中文描述）。
    • Few-shot：3-5 个"问题 → SQL"示例（覆盖聚合、分组、时间过滤、TopN）。
    • User：当前问题 + 槽位 JSON。
  • 输出约束：要求 LLM 输出 JSON，包含 sql、chart_type、explanation。
  • 校验：sqlglot 解析 AST，递归检查仅含 SELECT、表/列在白名单。

3.4 洞察引擎（Insight Engine）

  • 统计计算层（不依赖 LLM）：
    • 环比/同比：(本期 - 上期) / 上期。
    • Top-N 占比：Top-N 之和 / 总计。
    • 异常检测：z-score = (x - μ) / σ，|z| > 2 标记异常。
  • 叙事生成层：将统计结果交由 LLM 生成自然语言洞察，要求"结论 + 数据支撑"。

3.5 可视化引擎（Viz Engine）

  • 图表选择：基于数据行列特征的规则引擎（见 FR-C1）。
  • 输出：返回 ECharts 配置 JSON（前端渲染）+ matplotlib 图（导出用）。
  • 配色：统一色板，保证图表风格一致。

3.6 报告 Agent（ReportAgent）

  • 章节规划：LLM 根据报告主题生成章节大纲。
  • 逐章生成：每个章节调用问数 Agent 获取数据 + 洞察引擎生成洞察 + 可视化引擎生成图表。
  • 组装：Jinja2 模板将各章节内容拼装为 HTML 报告。

5. 关键技术决策

决策 1：NL2SQL 不做模型微调，采用 Prompt + Schema + Few-shot

理由：MVP 阶段数据量与标注成本有限；通用大模型 + 良好 Schema 描述 + Few-shot 示例已能覆盖大多数销售分析查询。后续可根据实际 badcase 积累微调语料。

保障：本地 AST 校验兜底，错误 SQL 不会执行；失败自动重试。

决策 2：使用 DuckDB 作为分析引擎，而非独立数据库服务

理由：销售数据通常为 CSV/Excel 文件，DuckDB 可直接对文件执行 SQL，无需建库建表运维；分析查询性能优于 SQLite；嵌入式部署简单。

适用边界：单表/少量表、GB 级以内数据。若后续数据量增大或需多表复杂关联，可迁移至 PostgreSQL/ClickHouse。

决策 3：Agent 编排使用 LangGraph 而非纯 LangChain Chain

理由：问数链路存在条件分支（是否澄清、校验是否重试）和循环（重试），LangGraph 的状态图模型更适合表达此类流程，状态显式可追溯，便于调试。

决策 4：图表渲染以前端 ECharts 为主，后端 matplotlib 为辅

理由：ECharts 交互体验好、渲染性能佳，适合在线展示；matplotlib 用于生成 PNG 供导出。后端不承担渲染压力。

决策 5：LLM 调用走 OpenAI 兼容 HTTP 接口，不绑定厂商 SDK

理由：DeepSeek、Qwen 等国产模型均提供 OpenAI 兼容接口，用 requests 封装最小调用层可灵活切换模型，避免依赖特定 SDK 的版本与接口变动。

7. 实施路线

阶段目标关键交付物
阶段 1：数据与 Schema 加载销售数据，搭建可查询的数据层 DuckDB 数据加载、Schema 自动推断、字段描述配置
阶段 2：问数核心链路 实现自然语言 → SQL → 结果 → 表格 意图路由、槽位抽取、NL2SQL、SQL 校验执行、表格展示
阶段 3：多轮与可视化 支持上下文追问与图表展示 会话状态管理、澄清流程、图表自动选择与渲染
阶段 4：洞察与报告 实现自动洞察与报告生成 洞察引擎、报告章节规划、报告组装与展示
阶段 5：体验优化 流式响应、导出、异常处理完善 SSE 流式输出、报告/图表导出、全链路异常处理
